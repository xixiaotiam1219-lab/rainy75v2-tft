# 测试与验证说明

为了保证改固件和写界面时尽量少踩坑，仓库搭建了三层纯本地的自动化检查（都不需要连接真实键盘）。这里也把「自动测试覆盖了什么」和「实机上还差什么验证」摆出来说清楚。

---

## 1. 基础自动化单元测试（CI 每次必跑）

直接运行下面几条命令（不需要原厂固件或 Clang，也不碰真实硬件）：

```sh
python -m unittest discover -s tests -p "test_*.py"
npm test
python tools/check_release.py
```

目前一共覆盖 **5 个 Python 用例 + 31 个 Node 用例**，包括：
- **协议与烧录安全**：`BE 1A`/`BE E4` 帧长度和校验、旧版 `0x0357` ACK 兼容、错误目标芯片拒绝擦写、IAP 全字节及末尾重叠块校验、旧固件写入前拦截、GIF 上传尺寸检查与覆盖确认。
- **素材与字库**：三套内置主题 GIF 逐帧校验（全帧尺寸、`disposal=1`、不透明及歌词标记像素 `(22, 39)`），并检查解码像素与绘图源码一致、仓库素材与生成器一致；拒绝恢复背景或增量矩形的回归文件。另有大图标尺寸和居中检查、`R75F/2` 字库索引有序性、双 CRC32 校验与未知字回退。
- **歌词扩展与桌面端**：QQ / 网易云歌手别名、Live/Remix/翻唱版本剔除与时长容差匹配、退避重试、异步切歌防覆盖、NFC 字形映射、网易云 Elog 字节解析与进度重建、USB 描述符与包长度严格核对、20/40px 字号切换及旧固件兼容、字库定点替换（`OP 27`）前置校验/排队/失败/超时恢复，以及离线控制台的持久化测试。

## 2. 无头浏览器 UI 烟雾测试（可选）

安装 Playwright（不是运行网页的工具依赖，只是拿来自动点页面和截屏）：

```sh
npm install --no-save --package-lock=false playwright@1.56.1
npx playwright install chromium
node tests/browser.smoke.mjs
node tests/lyrics-console.smoke.mjs
```

如果本地已经有 Chrome 或 Edge，可以通过环境变量 `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` 指定可执行文件路径，省去再下载一遍 Chromium。测试会用 Mock WebHID 和离线演示模式检查：
- 桌面端与手机端页面布局是否错位溢出；
- 像素工作台编辑/导出 `keys.json`、模拟 `V7.1` 对时流程以及旧固件拦截提示（生成 `assets/studio.png`）；
- 歌词控制台的 20/40px 字号切换、偏移滑块/数字输入/归零按钮与切屏交互（生成 `assets/lyrics-console.png`）。

## 3. 本地 ARM 指令级仿真（需要 Unicorn）

如果你本机有匹配的原厂固件并编出了 `build/ips-lyrics/`，还可以用 Unicorn CPU 模拟器直接跑编译出来的真实 Cortex-M4 机器码：

```sh
python -m pip install -r requirements-model.txt
python tools/test_lyrics_model.py --preview assets/player-pink.png
```

脚本会接管并模拟底层的 FatFs 文件系统、动态内存分配器、LCD DMA 忙标志和串口发送，实打实执行刚编译好的 `.bin` 机器码，重点验证：
- 只读芯片容量/系列查询（`1024KiB / 0x0D`）；
- 按键显示、Shift 符号转换与松开保留；
- 96 字独立歌名滚动、下一句位图缓存复用、每个 GUI 周期最多读 4 个字形的 I/O 上限、内存分配失败时的画面保护、切回按键页时资源释放；
- `0.2.0-alpha.2` 新增验证：同一份 `FONT.BIN` 同时渲染 20px 歌名和 40px 当前句（切换字号不重新读字形、不增加堆分配），以及 `OP 27` 固定 `FONT.BIN` 替换在未暂停时拒绝、旧头部不匹配时保留文件、匹配后关闭句柄只删 `FONT.BIN`、`OP 5` 恢复时取消未执行队列，并导出 `player-pink.png` 与 `player-pink-20.png` 预览图。

## 示例机器人闪烁的离线复现

旧公开示例每帧都是完整不透明图，但采用 `disposal=2`。对匹配 SHA 的原厂 IPS 执行真实 reset 初始化后，GIF 解码入口 `0x0805A54C` 跳到 RAM 的 `0x2003EE74`；其中 `0x2003EE7C..0x2003EF28` 在上一帧处置方式为 2 时，先用背景色清空 RGB565 帧面。原厂 worker `0x0805B244` 在状态 0 解码索引（调用点 `0x0805B310`），状态 1 才转换为 RGB565（`0x0805B2CA`），状态 2 提交 DMA（`0x0805B282`）。

两次 worker 调用之间，`firmware/ips/native_ui.c` 和歌词版对应文件的 `rainy_hook_image` 会在按键/状态变化时复用同一帧面进行脏刷新。这时若底图刚被处置方式 2 清空，刷新只补上动态字母与顶栏，机器人和边框便一起消失，直到下一轮转换恢复。`disposal=1` 保留上一张完整底图，避开这个窗口；同时必须显式写全帧，保留歌词切页所需的标记像素。

用本机合法原厂输入和模型依赖，可运行：

```sh
python -m pip install -r requirements-model.txt
python tools/test_gif_disposal_model.py --stock inputs/ips-stock.bin
```

此脚本执行原厂初始化及处置分支的真实机器码，三主题均复现处置方式 2 清空帧面、方式 1 保留帧面的差异；在文件读取及 LZW 解码开始前停止，不包含第三方固件。它不模拟完整解码或物理调度，不能替代受影响设备覆盖新 GIF 后的实机确认。更新仅涉及公开 GIF、生成/检查工具、测试及文档，固件与字库保持原版本。

## 4. 实机验证现状与待确认项

仿真和单测只能说明代码逻辑和内存边界没跑偏，不能完全替代真实硬件通电运行。目前实机情况如下：

- **同源歌词与替换功能**：在开发用机（`1024KiB AT32F435 / 4MiB 外置 Flash`）上完成过全字节烧录校验、20/40px 布局切换、旧字库校验删除与新字库上传提交，以及 QQ 音乐后台同步。一段 30 秒听歌观察里，7 次换句从后台发包到屏幕提交完成耗时约 `152~432 ms`（中位 `245 ms`，这是文字提交给屏幕缓存的耗时，不是按键输入延迟）。
- **尚待更多实机验证的部分**：
  1. 主控 `V7.1` 的校时有效标记写入修正，目前通过了指令仿真与网页流程测试，还待实机烧录后完整核对；
  2. 公开源码重编出来的默认字库与三套机器人主题（以及 `OP 27` 排队取消分支），还需实机看一遍最终显示效果；
  3. 网易云音乐最新桌面客户端的 Elog 本地进度重建，还待实机实际跑几首歌核对；
  4. 跨批次设备在长时间休眠、反复切换 2.4G/蓝牙模式下的稳态功耗与表现，暂未全部覆盖。

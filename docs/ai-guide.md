# 用 AI / Agent 帮你做外设

把这个仓库作为工程上下文，再描述设备、已有固件和期望结果，比直接让 AI “写一版能刷的固件”更容易得到可检查的工作。下面的提示词可复制到 Codex、Claude Code 等工具。

先准备自己的合法原厂输入、准确硬件信息和恢复条件。不要把凭据、私人角色图、设备序列号或完整个人日志作为公开上下文提交。

## 提示词一：做一套自己的像素主题

```text
你在 rainy75v2-tft 仓库工作。先读 README.md、AGENTS.md、
docs/customization.md 与 docs/compatibility.md。

目标：制作一套 [配色与风格] 的屏幕主题，保留时钟、电量、连接图标、
大单键显示，使用项目原创机器人，或使用我明确提供且有权使用的素材。

请先检查 profiles/keys.json、profiles/themes.json、tools/assets.py。
修改点阵与主题，生成 320×172 软件预览，标明它不是实机照片。
图标要按可见像素居中，检查左右 Win、Enter、方向键、PgUp/PgDn。
先交付预览和改动文件，不自动连接硬件、上传素材或烧录。
运行适用测试，区分测试通过与尚待实机确认的部分。
```

## 提示词二：定位显示或校时问题

```text
先读本仓库的使用、兼容性、协议和恢复文档。
问题现象：[准确描述]；连接方式：[USB / 2.4G / 蓝牙]；
主控与屏幕版本：[版本或未知]；是否关过电源或重刷：[说明]。

请区分 PC→设备传输、主控 RTC、校时记录、主控→屏幕快照、
屏幕本地秒数插值和最终绘制，不要把横线一概归因于 RTC 停走。
优先检查源码与已有日志。若需要真实设备读写，说明目标和操作；
只有我的明确授权范围内才执行，不通过重校时掩盖原始失败现场。
给出文件/函数证据，设计一个能区分原因的最小验证；
不要猜 RAM 空闲地址、擦除后读值、GPIO、晶振或恢复入口。
模拟结果只写为模拟结果；不能确定时直接列出未知项。
```

## 提示词三：给界面增加一个状态字段

```text
目标：增加 [状态字段]。先检查它是否已经有设备原生通知，
以及是否必须依赖电脑后台。先给出数据来源和所有权：由谁更新、何时失效。

请阅读 firmware/ips、firmware/main、web/protocol.mjs 和构建边界。
保持动画与素材本地缓存，动态状态只传必要的数据。
核对 ROM/RAM 容量、报文长度、序号、校验、忙状态与 DMA 缓冲区生命周期。
先实现可离线验证的解析和渲染，不在中断中加入等待式绘图或无限重试。
不要移除原厂输入哈希、目标 PID 或地址边界校验来让构建“通过”。
明确哪些是新功能、哪些仍需硬件验证；不要自动推送或烧录。
```

## 提示词四：把方法迁移到另一块外设

```text
设备：[准确型号]；屏幕/MCU：[已知型号或未知]；
连接与原厂开发资料：[来源]；我拥有的源码/固件：[说明]。

我想借鉴 rainy75v2-tft 的“本地缓存动画 + 少量状态更新”方法，
实现 [具体场景]。不要直接复用 Rainy75 的绝对地址、PID、帧格式或供电假设。
先列出可复用的主机逻辑、必须重新实现的设备驱动和缺失资料。
优先使用官方 SDK、开发板和公开接口，先做模拟或可恢复的原型。
给出最小通信协议、状态失效机制、带宽/内存估算和验证步骤。
如果涉及云 API，密钥留在电脑或服务端，不放到固件、截图或公开日志中。
```

## 提示词五：为自己的分支准备开源

```text
请先阅读 LICENSE、DISCLAIMER.md、THIRD_PARTY_NOTICES.md 和 CONTRIBUTING.md。
检查本次改动的自有源码、文档、素材和依赖，保留原有作者署名。
不要提交原厂 BIN、SDK archive/blob、厂商网页客户端、设备日志、
私人校时记录、账户密钥、私人角色或未经确认授权的衍生素材。
更新 README 截图，标注软件预览/模拟/实机验证的区别。
运行适用测试与内容检查，列出已知问题，不将 alpha 写为稳定版本。
准备可审查提交；只有我指定发布目标并授权时才向远程推送。
```

## 怎样判断 Agent 的结果是否可信

查看它有没有提供实际文件、构建结果和具体证据；确认它使用的是你的版本，而非“同芯片应该一样”的推测。让它解释剩余未知项，不必要求它把所有失败都包装成成功。

对硬件项目而言，**源码可编译、模拟可运行、刷写可校验、实机可工作、休眠与断电可保持**是不同的验证层次。AI 能减少重复劳动，但不能替代缺失的供电、电路、恢复条件或物理观察。
